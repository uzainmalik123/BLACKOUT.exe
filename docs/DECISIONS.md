### D-01: Pivot to an incident-response game
- **Context:** (2026-11-08) Reanimator raised dead repos so Death could attack them. Any agent can revive a repo on its own, so the product added nothing, and the UI had drifted into a pile of screens with no vision.
- **Decision:** the entry becomes a horror-themed incident-response simulator: a timed briefing, then Death attacks with real recorded attacks while the player defends with real actions; Death is driven by a rules-based Director; souls (data) and heartbeat (business) meters; three difficulty levels as dials on one scenario. Details and open questions are in `docs/GAME_PLAN.md`.
- **Consequences:** Poltergeist's engine isn't used. Kiro tokens are still saved for the demo.

### D-02: Fresh start on main
- **Context:** (2026-11-08) The old code is kept whole on the `failed` branch, so main only needs what the game uses.
- **Decision:** deleted `reanimator/`, `poltergeist/`, the committed `graphify-out/` cache and the three old workflows. Kept the project skeleton (moved to `game/`: package, Vite, TypeScript, ESLint and Vitest configs), the secrets guard and its workflow, the root env template (trimmed to LLM keys), `.claude/` skills and the licence. A new `Game CI` workflow provides the required `health` check.
- **Consequences:** pieces worth bringing back from `failed` when a task needs them: `reanimator/src/render/` (dot-matrix core), `reanimator/server/sse.ts` + `event-log.ts` (live streams), `reanimator/server/guard.ts` (loopback guard), `poltergeist/packages/core/src/compiler/llm.ts` (Groq/Ollama/Bedrock/Claude). The record-and-replay idea (`recorder.ts`, `shared/recording.ts`) is reused as a concept, not as code. The title still says "RE:Animator" until the team picks a name.

### D-13: The hackathon rules in the PRD
- **Context:** (2026-11-09) The rules require a working URL, a `/.kiro` folder, a video under 3 minutes without third-party trademarks or copyrighted music, and a write-up judged on how well Kiro was used. Kiro credits (about 4000) can't build the whole game, so Claude builds too.

- **Consequences:** about 1500 credits for development, 2500 for in-game use, judges and the demo, until KI-02 measures the real cost. KI-04 (hosting) becomes major.

### D-14: The grill gate
- **Context:** (2026-11-09) On Reanimator the user often asked to be grilled and to "take all the recommended options" in the same message. The agent then answered its own questions, and the project drifted into things nobody had actually decided.
- **Decision:** if a message asks for grilling (or any design questions) **and** to take all recommended options in the same breath, the agent refuses that combination, asks the questions with its recommendations, and stops. Only after the user has seen them may they say "take the recommended ones" or answer.
- **Consequences:** a rule in `AGENTS.md` and Kiro steering; the old Claude memory saying the opposite is removed.

### D-15: The recording format
- **Context:** (2026-11-17) REC-02 says each move variant is stored as one JSON events file, but not what's in it. The replay engine (SYS-03), the shell (SYS-09) and the souls meter (SYS-05) all read it, so it's fixed before the converter is written.
- **Decision:** one file `game/src/recordings/<MOVE>.<variant>.json` (e.g. `ATK-03.a.json`), typed in `game/src/recordings/format.ts`:
  - **Header:** `format: 1`, `move`, `variant`, `label`, `recordedAt` (ISO, run start), `durationMs`, `attackerIp`, `juiceShop` (image tag), `tool`.
  - **`events`**, sorted by `t` (ms since the run started, `0 ≤ t ≤ durationMs`), each one of:
    - `access`: one nginx request as fields (`ip method target protocol status bytes referer userAgent requestTimeMs`), not the rendered line: the replay engine stamps game time and renders the `combined` line itself.
    - `app`: one Juice Shop log line, verbatim. The window is the run plus 2 s after the tool exits (the time `record.sh` waits for logs to flush); lines outside it are dropped, and so are Juice Shop's scoreboard lines (`Solved … challenge`, `Cheat score …`): a real shop doesn't log them.
    - `db`: one row inserted, updated or deleted (`table`, `key`, `before`/`after`), from diffing the before and after snapshots, minus Juice Shop's scoreboard table (`Challenges`). `key` is `id` when the table has one, else `rowid`. An `insert` carries the whole row in `after`, a `delete` the whole row in `before`, and an `update` only the columns that changed, in both. Cell values are strings, numbers or `null`; a binary value (BLOB) becomes the string `base64:<data>`. Only tables in both snapshots are diffed: a table created or dropped during the run produces no events. Snapshots only bracket the run, so these are stamped at the run's last access event.
    - `file`: one file added, changed or removed under `uploads/` (`path size sha256`, and `contentBase64` only when ≤ 64 KiB), stamped like `db`.
    - `exfil`: rows that left the building in one response (`table`, `keys`, `columns`), found by matching the attack tool's own traffic log to the access log request by request; the converter refuses a run where the two disagree. Today only sqlmap's `-t` log is read, for `Users` emails and password hashes; a move made with curl records no `exfil` until it captures its responses too.

### D-65: Customers in the game (SYS-19) and the backlash model (closes KI-60, KI-61, replaces D-46 ruling 4)
- **Context:** (2026-11-21) REC-06 is recorded (D-61, D-62) and D-60 says SYS-19 plays it under everything from a pool shared with Death and the minions. D-46 left the feature-off drains as fixed weights "until SYS-19 measures the cost" (KI-79). The team's model for that cost, in their words: every customer request that fails because of the player costs a little heartbeat, so the cost follows real usage (search off hurts a lot, `/ftp` off almost nothing); failed customers complain (support tickets for the comms console, angry feedback lines in the log); churn: sustained failures lower the heartbeat's maximum a little, permanently; tuned so that "everything off" still flatlines within about 10 minutes, search off alone in about 15, and toggling never pays.
- **Decision** (every number _(tune)_, in `game/src/engine/config.ts` under `customers`):
  1. **The loop.** `customers.ts` plays `traffic/CUST.a.json` (loaded by SYS-19 itself through the library's `CUST` entry, D-62) at its recorded speed × 30, from the start of the run, and starts it again the moment it ends (601 s recorded = 10 real minutes). Each loop plays a fresh **seeded subset of the recording's 64 shoppers**: `customers.share` of them (Easy 0.2, Medium 0.4, Hard 0.8 = 13, 26, 51 addresses, about 1, 2 and 4 access lines per real second on average; the recording itself has lulls, so a minute can be half that). The subset keeps the recording's mix: shoppers are grouped by the rarest thing they do (a sign-up, a complaint, a checkout, a login, a search, just browsing) and each group gives its share (largest remainders first), so a loop always has about the same number of sign-ups and checkouts and a flag's cost doesn't swing on who was sampled. A shopper not in the subset leaves no line that loop. Customers draw from their own seeded stream (`world.customers.rng`, like the taps), so Death's and the minions' draws don't move.
  2. **The shared pool (D-60).** `pool.ts` owns the three documentation ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24). Each shopper in a loop gets one address drawn from all three, avoiding every address a committed move or minion recording writes a line from (Death's recorded starts stay his; a wave's many addresses too, D-27), every address Death's replays and the minions' waves hold at that moment, and the other shoppers'; the same recorded address keeps its pool address for the whole loop (a visit is one address and one browser; the same shopper may come back later in the loop). A shopper may land on an address the player blocked earlier (dynamic addresses change hands): that is IP blocking's collateral, and the ticket says so. The other way round, Death's fresh addresses (D-24), the minions' wave addresses, the proxy pools (D-46) and the taps' scraper lines never take an address a customer holds: where one of their seeded draws lands on a customer's address they step to the next free one instead of drawing again (`bump`), so every later draw of that stream stays where it was and seeded runs keep their story. A range therefore never gives anyone away: a third of the customers sit in TEST-NET-3 next to Death.
  3. **What a customer request is**, by method and path (`classify` in `customers.ts`, from PR #73's list): `search` (`GET /rest/products/search?q=<word>`; the empty `q=` is the product list, a `page` request); `login` (`POST /rest/user/login`, `whoami`, `saveLoginIp`); `signup` (`POST /api/Users/`, `/api/SecurityQuestions/`, `/api/SecurityAnswers/`); `basket` (`/rest/basket/<id>`, `/api/BasketItems…`); `checkout` (`/api/Addresss…`, `/api/Deliverys…`, `/api/Cards…`, `/rest/wallet/balance`, `POST /rest/basket/<id>/checkout`, `/rest/track-order/…`); `feedback` (`/rest/captcha/`, `POST /api/Feedbacks/`); `complaint` (`POST /file-upload`, `POST /api/Complaints/`); `password-reset` (`/rest/user/reset-password`, `/rest/user/security-question`); `ftp` (`/ftp/…`); everything else (`/`, the bundle, assets, config, languages, the product list, product details, quantities, reviews) is `page`.
  4. **How the world answers them.** In order: the plug pulled → the request never reaches the shop (no line, no cost: the plug's own drain is the cost, SYS-06). The shopper's address in the firewall → dropped (no line), a failure. A WAF rule matching the request → `403`, a failure: `block-user-agent` matches the browser's user agent (case-insensitive substring), `block-path` matches the method and the path with `*` as one segment (`/rest/products/*/reviews` matches a customer's review read; `PUT /api/Products` matches nothing a shopper does), the SQLi rule set matches a target with an injection token (`'`, `%27`, `union`, `select`, `--`: none in REC-06, so it never blocks a shopper). A rate-limited path (`rate-limit`, DEF-07 included) → `429` to an address that hits it a **third time within 15 recorded s** (`rateLimit.burst` 2, `windowMs` 15 000): the recording's typo-retriers trip it, returning shoppers don't. A disabled feature → `503` to its class: `search` off fails searches, `registration` off sign-ups, `uploads` off the complaint's `/file-upload` (the complaint text still posts), `password-reset` off resets, `ftp` off `/ftp`; the feedback CAPTCHA on fails nobody (REC-06's shoppers solve it). Otherwise the line plays as recorded, from the pool address, with the recorded status. A `403`/`429`/`503` line carries nginx's default error page size (153, 169, 197 bytes: estimates, like the taps' KI-59). Access lines are tagged `by: 'CUST'`.
  5. **The backlash** (`backlash` in `heartbeat.ts`), replacing D-46 ruling 4's feature weights (deleted from `config.ts`):
     - **Cost per failed request, by class** (`customers.cost`, the same on every level): `page` 0.1, `search` 1.5, `login` 1, `basket` 1.5, `feedback` 0.5, `complaint` 3, `password-reset` 2, `ftp` 0.5, `checkout` 4, `signup` 10. Taken from the heartbeat at once. A failed search is an annoyance; a failed checkout is a sale lost; a failed sign-up is a customer who never existed (REC-06 has 6 sign-ups in 601 s, so without that price turning registration off would be nearly free).
     - **Complaints.** A shopper's first failure in a loop files one **support ticket** (`world.tickets`: when, their address and browser, what they were doing, the status they got, a line of text by class) and logs a `ticket` event; the comms console lists them.
     - **Churn.** A shopper who fails a **second time in the same loop gives up** (`giveUpAfter` 2; a `page` failure, an asset, the product list or reviews not loading, annoys but doesn't count: what they were trying to do has to fail): the rest of their visit never comes (no more lines from them that loop), they leave **angry feedback** on the way out when they can reach the shop (a `GET /rest/captcha/` and a `POST /api/Feedbacks/ 201` line from their address, byte counts from REC-06's own feedback requests, and a `Feedbacks` row with rating 1 the player can `SELECT`; a dropped or `403`ed shopper can't, and only the ticket arrives), the heartbeat's **maximum drops by `churn` (1.0) for good** (`world.heartbeatMax`, from 100; the heartbeat never rises above it), and a `customer-lost` event logs it.
     - **No recovery while customers fail:** SYS-06's +2 per real minute waits until a real minute has passed since the last failure (`recoverAfterGameMs`), so a flag left off never nets out against recovery between two failures.
     - DEF-07's, DEF-09's, DEF-13's, DEF-14's and DEF-16's one-off dips stay (D-24); DEF-07's "real customers slowed" is now also the `429`s.
     - **Tuned on Medium, the committed recordings, whole runs over seeds 1–5:** everything off and left off flatlines the shop in 6.6–10.6 real minutes (seed 1: 10.1; the test allows 10.5), search off alone (the search door and the customers) in 13.3–15.3 (seed 1: 14.9; allows 16), search off with every other hole patched in 11.2–13.2. Customers alone, with no Death draining a door: search off 17.3, everything off 13.4. Easy has half the customers and so about half the cost per minute, Hard double (the dial is the volume, not the price). Toggling never pays: every minute a feature is off costs its customers, Death's visit freezes only while it is off (D-45), and churn stays. For scale: the login rate limit (DEF-07) answers `429` to 4–5 shoppers in 30 minutes (about 5 heartbeat, plus its dip); TAP-03's path block (`/rest/products/*/reviews`) answers `403` to every review read, about 1.2 a minute while it holds (KI-83); a user-agent rule for `Mozilla` or every pool address blocked is the plug by another name (a flatline in 4–6 minutes).
  6. **Not applied, not souls.** The recording's `db` events (6 sign-ups, baskets, items, addresses, cards, feedbacks, complaints, quantities, 18 `lastLoginIp` updates) are **never applied** to the world or the DB: customers are never souls (the 325 seed rows stay the souls, SYS-05), the accounts and baskets they'd create never exist, and KI-61's proxy address never reaches the world (closes KI-61). The only rows customers write are the angry `Feedbacks` of rule 5.
  7. **The Done-when's share.** REC-06 whole is about 5 lines a second; Death's scan alone is 4,756 lines in 13 s, so no share of the recording makes customers 60 % of a whole idle run. SYS-19's check reads "60 % of the access-log lines outside Death's scan (ATK-01)", which the idle Medium run meets; the scan is thousands of lines in seconds in real life too.
  8. **Open, logged:** REC-06 has no forgot-password and no `/ftp` visit, so `password-reset` off and `ftp` off cost nothing until a shopper is recorded doing either (KI-82); MIN-03's one closing rule, `rate-limit /api/*`, would `429` shoppers' own bursts of `/api/` calls, and TAP-03's path block `403`s every review read (KI-83); the error pages' byte counts are estimates (KI-84); WAF user-agent rules are matched literally against customers but symbolically against Death (KI-85).
- **Tests:** `customers.test.ts` (unit tests on a made-up traffic fixture, then the committed CUST.a): the loop restarts, each loop plays its share from fresh pool addresses in all three ranges, never an attacker's, never one Death or a wave holds, and Death's fresh address never a customer's; every class of PR #73's list is classed; search off answers `503` to searches and nothing else, registration off to sign-ups, uploads off to `/file-upload` only; a rate limit `429`s the third login in 15 s; a user-agent rule `403`s every browser it names and a path rule the paths it covers; a blocked address writes no line; the plug writes no line and costs nothing; a failure costs its class, files one ticket per shopper per loop, a second failure churns (max drops, the rest of the visit is gone, the feedback line and row appear) and recovery waits a minute; the DB changes are never applied and the souls never move; the idle Medium run's customers are ≥ 60 % of the lines outside the scan at about 2 lines a second (Easy about 1, Hard about 4). `heartbeat.test.ts`: the feature weights are gone, `backlash` costs and churns, the maximum caps recovery. `exploits.test.ts`, customer-aware cheaters on the committed recordings with customers: everything off (a flatline in 7–10.5 min, with `503`s, tickets and churn as the cause), search off with every other patch (9–16), search off alone on the search door (12–16), toggling every 5 s (a loss), the search flip on the search door with customers (a loss, search tickets), blocking every new address as it appears, customers included (he goes to proxies, the shop flatlines inside 10 minutes, the blocked customers' tickets name blocked addresses), a user-agent rule for `Mozilla` (every customer request `403`, none served, a flatline inside 8 minutes: no win), a path rule over `GET /rest/*` (no win, `403`s, POSTs still through), and DEF-07 (a few `429`s on the login only, nobody lost). The engine's WAF stoppers stay symbolic (D-24: a rule pattern names the PRD's rule), so a `Mozilla` rule stops no Death move while the customers are matched literally (KI-85). The cheap-actions property runs with customers on too (the made-up traffic), as does the engine-invariants property. `pool.ts` unit tests: `drawAddress` and `bump`. Changed expectations: the SYS-06 sims' feature-weight terms are gone; the ATK-03 access-log line sits among customers' lines; `initialWorld` differs between seeds in the customers' stream too.
- **Consequences:** KI-60 and KI-61 closed; KI-79's interim weights gone (D-46 ruling 4 superseded). ### D-91: DEF-04 from the shell

### D-92: SQL in the shell
- **Context:** (2026-11-21) DEF-02, DEF-08 and DEF-14 are the only SQL uses in the PRD; the shell needed a rule for everything else.
- **Decision:** `sqlite3 <db> "<sql>"` runs on the Engine's copy. `UPDATE Users SET deletedAt…` sends DEF-08 and `DELETE FROM Users…` sends DEF-14, once per matched account. Any other write is a read-only error and changes nothing. Also supported: `-header`, the dot-command `.tables` and `.schema [table]`.
- **Consequences:** The shell finds the matched accounts by running the statement's WHERE clause as a SELECT first. Interactive `sqlite3` (no SQL argument) stays unsupported.

### D-93: Shell syntax beyond pipes and `>`
- **Context:** (2026-11-21) SYS-09 said "pipes and `>`" only, but `rm uploads/*` and `cd ~` are what a responder types.
- **Decision:** Added: `*` globs (one path segment, not dotfiles, sorted, left as typed when nothing matches, not expanded inside quotes) and a leading `~` (the start directory `/srv/juice-shop`). Still syntax errors: `;`, `&&`, `>>`, `<`, `2>`, `$VAR`, `$(…)`, backticks. SYS-09 and the steering file are edited to match.

(Found in the build, 2026-11-22: a redirect target's `~` always resolves under `/srv/juice-shop`, which is outside the Writable_Area (D-90), so `> ~/x` is always `Permission denied`.)

### D-94: Shell session
- **Context:** (2026-11-21) The shell spec had open questions on the start directory, `complete` and the unknown-command text.
- **Decision:** The shell starts in `/srv/juice-shop`. `complete` exists on Easy only and is absent (undefined) on Medium and Hard. An unknown command prints `<name>: command not found`.

### D-95: `run()` result: `exitCode` and `clear`
- **Context:** (2026-11-21) `{ output }` can neither clear the screen nor tell success from failure, which the shell spec's error cases and the terminal window both need.
- **Decision:** `run` resolves `{ output: string; exitCode?: number; clear?: true }`. `clear` is `true` only for the `clear` command, with an empty `output`. `exitCode` is 0 on success, 1 for a failed command (and `grep` with no match), 2 for a syntax error, 127 for `command not found`; omitted counts as 0. ENGINE_API §5 is edited; screens may ignore both fields.
- **Consequences:** The terminal window clears when `clear` is true. Nothing else depends on `exitCode` yet.

### D-96: The `awk` subset

- **Context:** (2026-11-21) Real awk is large; the shell needs only what the DEF-01 log searches use.
- **Decision:** `awk [-F<sep>] '[/regex/] {print <expr>[, <expr>…]}'` where each `<expr>` is `$0`, `$N`, `$NF` or `NR`; several expressions are joined by one space. Anything else prints `awk: unsupported program`. (Amended 2026-11-21 by the team: the first version allowed a single expression.)
- **Consequences:** `{print $1, $7}` works; `{c[$1]++}`, `BEGIN`/`END` and arithmetic don't. If the scenes need more, change this decision first. (Found in the build, 2026-11-22: `-F` takes a single character; a longer separator such as `-F'::'` prints `awk: unsupported program`, as `cut -d` also takes one character.)

### D-97: `systemctl` details
- **Context:** (2026-11-21) D-22 made `restart` a stop then a start; two cases were open.
- **Decision:** `restart` always attempts the stop and then the start, even when the stop is refused (nginx already stopped). Only the `nginx` unit exists; any other unit prints `Unit <name>.service could not be found.`.
- **Consequences:** None.

### D-98: Terminal commands and game time

- **Context:** (2026-11-21) DEF-01 to DEF-03 are "Game time" actions in the PRD, but the Engine had no way to see that the player read the logs, the database or an upload. The report (SYS-11) grades time-to-notice.
- **Decision:** A command takes no game time of its own. A command line that reads a log, the database (`sqlite3` SELECT, `.tables`, `.schema`) or `uploads/` sends one action per **kind of resource read**, each at most once per line, whatever the number of commands in a pipeline: DEF-01 for a log (`query` = the whole command line), DEF-02 for the database (`sql` = the first SQL text read), DEF-03 for uploads (`path` = the first uploads path read, absolute). A pipeline therefore sends at most three. A line that fails before reading anything sends nothing; `tar czf` sends DEF-05 only (its source reads send nothing); `cp` from uploads sends DEF-03. (Amended 2026-11-21 by the team: the first version sent one per reading command.)
- **Consequences:** The event log gains up to three `action` events per line, so tests that compare worlds must allow for them. The shell sends DEF-04 `active` as D-91 says; KI-90 (the Engine tipping off on any address) stays open for the Engine team.

### D-102: The database file as a file
- **Context:** (2026-11-22) The spec lists `juiceshop.sqlite` in the file system without saying what `cat`, `cp`, `tar`, `sha256sum` and `ls -l` do with it.
- **Decision:** It is a read-only file whose bytes are `(await engine.db()).db.export()`, taken when needed. Raw reads send no DEF-02 (that action is for SQL). `cat`, `head`, `tail` and `grep` on it print the bytes decoded and sanitized (D-106). `rm`, `cp` onto it and `>` onto it are `Permission denied`.

### D-103: SQL execution rules
- **Context:** (2026-11-22) D-92 fixed which writes exist but not how statements are split, which reads are allowed or what the errors say.
- **Decision:** (1) The argument is split on `;` outside quotes and parentheses; statements run in order and the first error stops the rest. (2) Reads: `SELECT`, `WITH` without a write keyword, `VALUES`, and `PRAGMA table_info|table_xinfo|index_list|foreign_key_list|database_list`. (3) A write is recognised only as `UPDATE Users SET deletedAt = <expr> [WHERE <w>]` or `DELETE FROM Users [WHERE <w>]`; `OR`, `RETURNING`, `ORDER BY`, `LIMIT`, `FROM`, a second assigned column or an alias make it a read-only error. (4) The `<expr>` is evaluated while finding the matched rows; if it gives NULL or `''` the statement is a read-only error, since no action unlocks an account. (5) Messages: `Error: attempt to write a readonly database` for refused writes, `Error: <SQLite message>` for invalid SQL, `Error: database is unavailable` when `Engine.db()` rejects.
- **Consequences:** The WHERE clause is run as a SELECT on the Engine's database to find the emails for DEF-08 / DEF-14.

### D-104: Quoting
- **Context:** (2026-11-22) R3 lists the syntax errors but not what quotes do.
- **Decision:** No backslash escapes. Inside single and double quotes every character is literal, `$` included (D-93 forbids `$` only outside quotes). Adjacent quoted and unquoted pieces join into one word. A word quoted anywhere is never glob-expanded. A redirect target gets `~` expansion only. Outside quotes `&`, `(`, `)` and a lone `$` are syntax errors.
- **Consequences:** The pretty-printer drops quotes that carry no meaning, so the parse → print → parse round trip holds. (Found by Property 1, 2026-11-22: quoting a word that holds `*` or starts with `~` would mark it literal and change its meaning, so the printer leaves such a word bare unless the lexer would misread it, e.g. `~é` or `*#`.)

### D-105: Regex dialect and guard
- **Context:** (2026-11-22) `grep` and `awk` take patterns from the player, and a catastrophic pattern would freeze the page.
- **Decision:** `grep` without `-E` is a basic regex: `. * ^ $ [ ]` are special, `+ ? | ( ) { }` literal. With `-E`, and in `awk /re/`, the extended operators are special (a JavaScript `RegExp`). A pattern longer than 256 characters, with a back-reference, with a quantified group that itself holds a quantifier (`(a+)+`), or with a counted repeat above 255 prints `grep: unsupported pattern` (`awk: unsupported program`).
- **Consequences:** No timer is needed to keep `run` inside the 5 s bound of the robustness property.

### D-106: Output text, never markup (amends R1.4)
- **Context:** (2026-11-22) "No HTML tags" can't hold for echoed arguments or file content: an uploaded file may contain `<script>`.
- **Decision:** The shell adds no markup. Every character below U+0020 except newline and tab, and U+007F, is shown in caret notation (`^[` for ESC), as `cat -v` does. Other content is unchanged. The terminal window renders `output` as text, never as HTML (added to `docs/SCENES.md`).
- **Consequences:** The R1.4 test checks the control-character rule and that lines the shell writes itself hold no `<`.

### D-107: Flags for commands with none in the PRD
- **Context:** (2026-11-22) Requirement 16 needs a defined flag list for every command.
- **Decision:** `ping -c <count>` (default 4, 1 to 20); `nmap -p <ports>` and `-sV`; `curl -I` and `-s`; `ss -t -l -n` and their bundles; `rm -r` only (no `-f`, no `-R`); `mkdir -p`. None for `cp`, `whois`, `date`, `history`, `help`, `file`, `sha256sum`. Any other flag is the unsupported-flag error.
- **Consequences:** The registry holds these; `man` prints them.

### D-108: `rm -r` in uploads, and several operands
- **Context:** (2026-11-22) DEF-15 removes one file.
- **Decision:** `rm -r <dir in uploads>` sends one DEF-15 per file below it, in ascending path order, and goes on after a refusal. `rm` with several operands (a glob included) handles them left to right, one action per uploaded file, and ends with exit code 1 if any failed. The directory disappears by itself when its last file is removed.
- **Consequences:** None.

### D-109: Archives
- **Context:** (2026-11-22) `tar czf` needs bytes to hash and a listing to print, without real compression.
- **Decision:** An archive is a deterministic byte string: the gzip magic `1f 8b 08 00`, then a canonical listing of entries (path, type, length, bytes). `sha256sum` hashes those bytes. `tar tzf` prints each source path in the order given, each followed by its descendants in ascending order, directories with a trailing `/` and the leading `/` removed, as real tar does. `file` reports `gzip compressed data`. A missing source prints `tar: <path>: No such file or directory`.
- **Consequences:** Same content, same digest, on every run.

- **Context:** (2026-11-22) The shell (D-91) sends DEF-04 `active` for every `ping`, `nmap` or `curl` on an IPv4 target and leaves the decision to the engine, but `engine/actions.ts` tipped Death off on every active lookup, so `ping 8.8.8.8` sped him up (KI-90). ### D-115: Relevance by outcome (replaces D-114 rule 2, closes KI-112)
- **Context:** (2026-11-22) D-114 judged a look relevant by what the player typed (an address or a path his moves requested), which was broad after the scan (KI-112) and blind to what the output actually showed. The team ruled: judge by outcome.
- **Decision** (`game/src/engine/assess.ts`, `rules/vocabulary.ts`):

### D-160: The shell's read actions carry what reached the screen (feeds D-115)
- **Context:** (2026-11-22) D-115 judges a read by the `shown` lines it passes. - **Decision** (`game/src/shell/tracker.ts`, `exec.ts`; R14.8):

### D-201: The Fly machine logs into Kiro itself, by device flow, on a volume (SYS-18; amends D-200 rules 3 and 4)
- **Context:** (2026-11-24) D-200 assumed a Kiro API key as the Fly secret. The user's plan cannot create one (Kiro's docs: "API key based authentication is only available for Kiro Pro, Pro+, Pro Max, and Power subscribers"). The other way kiro-cli signs in is its own login, which is a browser flow on a laptop but has a **device flow** for machines without a browser (`kiro-cli login --use-device-flow`: the CLI prints a URL and a one-time code, the user confirms it on any device, the CLI polls until it is authorised). The login is kept in kiro-cli's data folder (`~/.local/share/kiro-cli/data.sqlite3`, table `auth_kv`), which on a Fly machine is container disk: gone at every deploy and restart. - **Decision:**
  1. **The machine logs in itself, once, by hand**: after the first deploy, `fly ssh console -u node` (the server's user, so the login lands where the server reads it), `kiro-cli login --use-device-flow` with no other flag, pick **Use with Google** in the menu, open the printed `app.kiro.dev/account/device?user_code=…` URL on the laptop, confirm the code, `kiro-cli whoami`. Google is tried first (the credits are there); **Use with Builder ID** is the fallback (`--license free` skips the menu and forces it), with the warning that credits are per account: a Builder ID is a different Kiro identity from the Google login, so a run on it would spend that account's credits, not the Kiroween ones. If the login lapses, the same steps again.
  2. **The login lives on a volume**: `XDG_DATA_HOME=/data/xdg` in the image and in `fly.toml`'s `[env]`, which kiro-cli 3.5.0 honours (its data folder becomes `/data/xdg/kiro-cli/`, nothing lands in `~/.local/share`; proven in Docker, `docs/HOSTING.md` §1). The 1 GB volume `data` mounted at `/data` is no longer optional (`[mounts]` in `fly.toml`, `fly volumes create data --size 1 --region <primary_region>` once before the first deploy); the counters (`/data/runs.json`, KI-193) are on it too. The machine is pinned to the volume's region, which the team accepts: one machine, one region.
  3. **A root entrypoint, then `node`**: a Fly volume is mounted root-owned, so `scripts/container/entrypoint.sh` runs as root, `mkdir -p` and `chown`s the counters' folder and `XDG_DATA_HOME` to `node`, then `exec setpriv --reuid=node --regid=node --init-groups` (util-linux, in the slim image) with `HOME=/home/node` for the server. The server process is never root; `USER node` in the Dockerfile is replaced by the drop. Started as a non-root user already, the entrypoint just runs the command.
  4. **`GET /healthz` says the auth mode**: `kiroAuth: "key" | "cli-login" | "none"`, from `server/auth.ts`'s `watchAuth`: `kiro-cli whoami --format json` once at start-up (the D-200 log line) and then every 10 minutes (`AUTH_PROBE_MS`), cached, never an agent, never a credit; a change between probes logs `[kiro] auth changed: cli-login → none`. The field never fails the check (KIRO-09: the game plays on offline), and never carries the account's email. A lapsed login is seen there within 10 minutes; KI-203 says to look daily.
  5. **`KIRO_API_KEY` stays as it is and wins**: with the secret set nothing is probed and the mode is `key`. The HOSTING runbook keeps the key path as the alternative for a plan that has one.
- **What was tried in the local image** (kiro-cli 3.5.0, no credentials, nothing signed in): `--license free --use-device-flow` and `--license free --social google --use-device-flow` both print a **Builder ID** device page (`view.awsapps.com/start/#/device?user_code=…`): the `--social` flag is ignored under those flags. `--social google` alone starts the browser flow (a loopback listener on `localhost:3128` and `app.kiro.dev/signin?…`), fails with "Failed to open browser" and exits. The plain `kiro-cli login --use-device-flow` shows the four-entry menu (Builder ID, Google, GitHub, Your Organization) and **Use with Google** prints `https://app.kiro.dev/account/device?user_code=XXXX-XXXX&login_provider=Google` plus the code, then polls ("Waiting for authorization…"): the Google device flow Kiro's docs describe. That is the runbook's command. `KIRO_DATA_DIR` appears in the binary's strings but did nothing; `XDG_DATA_HOME` did.
- **Consequences:** `docs/HOSTING.md` is rewritten as one ordered runbook (flyctl → launch → volume → deploy → login on the machine → verify → the two SYS-18 runs). D-200 rule 3 (the key is the auth) becomes the alternative; rule 4 (volume optional) is reversed. `fly ssh console` without `-u node` would log root in, into `/data/xdg` as root-owned files: the runbook says `-u node` every time and how to repair. KI-203 (token lifetime of the device-flow login unknown), KI-204 (the volume's root ownership and the ssh session's environment are assumed from Fly's behaviour, not documented), KI-205 (which Kiro account a Builder ID with the same email is), KI-206 (the first agent start on the fresh volume once took 30 s).
